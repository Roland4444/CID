# Контроль исполнительной документации — Rust / Axum / Synology (MVP 0.4: нормативный контроль)

**Статус: исходный код прототипа, не аттестованная система строительного контроля.** Оригинальные файлы на Synology не изменяются. **Проверка орфографии и LanguageTool из первого этапа удалены.** Вместо неё добавлена система утверждаемых правил ГОСТ/СП/приказов и протокол результатов по каждому правилу.

**Ограничение верификации:** в среде подготовки не установлены `rustc` и `cargo`. Поэтому ниже описаны тесты для запуска в вашей среде; компиляция Rust-кода и его работа с PostgreSQL / Synology здесь пока **не подтверждены**.

## Что делает версия 0.4

1. Наблюдает за SMB-папкой Synology в режиме **только чтение**; раскладывает найденные файлы в проекты и комплекты по названиям директорий.
2. Архивирует копии оригиналов по SHA-256, хранит версии, историю повторных проверок и аудит.
3. Распознаёт DOCX, XLSX, PDF, JPEG/PNG (через локальные `pdftotext`, `tesseract`, `pdftoppm`). Классифицирует акты и другие документы; первоначальный каталог — **14 видов работ / 169 позиций**.
4. Проверяет комплектность только по выбранному и утверждённому инженером перечню. Исходные ссылки на НТД из предоставленных файлов не считаются автоматически действующими.
5. На странице **`/norms`** позволяет зарегистрировать требование НТД: вид работ, код документа, название, редакция, пункт, источник нормативного текста, условие и тип проверки. Правило сначала становится **черновиком** и не применяется до явного утверждения.
6. Применяет только утверждённые правила следующих видов:
   - `required_phrase` — поиск конкретного обязательного реквизита/фрагмента текста;
   - `forbidden_phrase` — выявление специально утверждённой как недопустимой ссылки или формулировки;
   - `required_pattern` — проверка структуры реквизита регулярным выражением Rust regex (например, наличие номера акта; **само выражение не является нормативом**);
   - `manual` — документированная проверка по нормативному пункту, выполнить которую автоматически пока нельзя.
7. Отдельно сохраняет все результаты утверждённых правил в `normative_check_results`, включая успешные **наблюдения**, предварительные несоответствия и результаты, требующие ручной проверки. В результаты включаются редакция, пункт и источник НТД.
8. Проверяет отдельные даты, формирует проект замечаний. Инженер подтверждает/отклоняет/закрывает замечания. Экспорт XLSX/DOCX/PDF включает обязательные четыре столбца.
9. Не заявляет, что весь документ соответствует ГОСТ/СП только потому, что найден ожидаемый текст. Если нет утверждённых правил, нет полного распознанного текста или необходимо проверить оформление/геометрию, результат — **«Требуется ручная проверка»**.

**Важно:** эта версия не сверяет полноценно фактические размеры с проектом, допуски ГОСТ, графические чертежи или подлинность сертификатов. Проверка структуры и нормативных фраз — **ограниченная автоматизация части требований**. Для полноценного ГОСТ-контроля нужны утверждённые тексты норм, оригиналы/шаблоны форм, правила по каждому виду работ и согласованные тестовые комплекты. Код содержит готовую точку расширения `src/norms.rs`.

## Размещение

**Рекомендуется внутренняя сеть компании, без публичного IP.** Debian 12 / Ubuntu Server 24.04; отдельная виртуальная машина, сервер или выделенный Linux-хост, соединённый с Synology по SMB 3.0; обратный HTTPS-прокси в локальной сети. Удалённым сотрудникам доступ через корпоративный VPN. Интернет и VPS не являются технической необходимостью. Не публикуйте PostgreSQL, SMB и HTTP Basic-auth сервер напрямую в интернет.

Стартовые ориентиры: 4 vCPU, 8 ГБ ОЗУ, 80–150 ГБ свободного локального диска (с учётом объёма временных OCR-файлов и сохраняемых версий), PostgreSQL 15+ и отдельный резервный архив на NAS. Для очень больших комплектов увеличьте объём диска и RAM; OCR требует наиболее существенных ресурсов. Это рекомендации, а не требования законодательства.

Текущий прототип использует только **одну** учётную запись через Basic Auth. Для эксплуатации необходимо добавить роли «Администратор / Инженер / Руководитель» и раздельные права, как требует исходное ТЗ. **Размещение в интернете до добавления ролевого доступа и дополнительных защит не рекомендуется.**

## Структура папок NAS

```text
/SHARE/Исполнительная документация/
  ЖК Северный/
    Земляные работы/
      ИД/
        АОСР №15.docx
        Реестр.xlsx
      ПД-РД/
        Чертежи.pdf
```

Приложение ожидает `WATCH_ROOT` на корневом каталоге с проектами. В проект создаётся одна запись на папку объекта, в комплект — одна запись на папку вида работ. В Bitrix24 проекты пока **не создаются**: это отдельная интеграция.

## Установка: Debian / Ubuntu без Docker

```bash
sudo apt update
sudo apt install -y build-essential pkg-config libssl-dev postgresql cifs-utils \
  poppler-utils tesseract-ocr tesseract-ocr-rus tesseract-ocr-eng \
  libreoffice-writer fonts-dejavu-core
# Установите Rust / Cargo штатным способом, соответствующим вашей ОС.
rustc --version
cargo --version
```

Создайте отдельную базу PostgreSQL и пользователя БД с уникальным паролем:

```bash
sudo -u postgres psql -c "CREATE USER idcontrol WITH PASSWORD 'CHANGE_THIS_DB_PASSWORD';"
sudo -u postgres psql -c "CREATE DATABASE idcontrol OWNER idcontrol;"
```

Создайте на Synology **пользователя только с чтением** необходимой SMB-шары. На Linux:

```bash
sudo mkdir -p /mnt/synology/id
sudo install -m 600 /dev/null /root/.smb-id-credentials
sudo nano /root/.smb-id-credentials
```

Содержимое файла учётных данных:

```ini
username=id_reader
password=YOUR_NAS_PASSWORD
```

Подключите ресурс:

```bash
sudo mount -t cifs //NAS_IP/SHARE /mnt/synology/id \
  -o credentials=/root/.smb-id-credentials,vers=3.0,iocharset=utf8,ro
mountpoint /mnt/synology/id
```

Для постоянного подключения используйте `/etc/fstab` и `x-systemd.automount`; подробный пример есть в предыдущем MVP. `WATCH_ROOT` должен указывать на **точку монтирования** при `REQUIRE_MOUNT=true`.

В каталоге проекта:

```bash
cp .env.example .env
# Измените DATABASE_URL, APP_PASSWORD, WATCH_ROOT и DATA_ROOT
nano .env
cargo fmt --all -- --check
cargo check
cargo test
cargo build --release
cargo run --release
```

В `.env.example` по умолчанию указано `LISTEN=127.0.0.1:8090`. Доступ по HTTPS организуется через `deploy/nginx.conf`; пример `systemd`-юнита в `deploy/id-control-axum.service`. При установке на сервер следите, чтобы системный пользователь приложения имел право читать mount и записывать только свой `DATA_ROOT`.

При первом запуске выполняются **идемпотентные** SQL-скрипты `migrations/001_init.sql`, `migrations/002_norms.sql`, `migrations/003_norm_patterns.sql`; старые документы и замечания не удаляются. Колонки прошлого MVP, связанные с орфографией, остаются в БД ради совместимости истории, но **не используются**.

## Первичная настройка проверки ГОСТ/СП

1. Откройте приложение внутри сети, создайте проект и выберите вид работ.
2. В комплекте отметьте обязательные по конкретному объекту пункты чек-листа.
3. Перейдите на `/norms` и создайте черновик требования. Укажите **точные** название, редакцию, пункт НТД и путь к имеющемуся утверждённому нормативному документу; при необходимости ограничьте применение одним кодом документа из каталога (например, `1.4`).
4. Ответственный специалист **сверяет текст нормы по оригиналу** и нажимает «Утвердить» (в прототипе это делает единственный авторизованный администратор; полноценное разделение полномочий ещё не реализовано).
5. Вернитесь в комплект и запустите повторную проверку. Результаты каждого правила появятся в отдельной таблице, предварительные замечания — в реестре на рассмотрение инженера.
6. При изменении нормативной базы отзовите старое правило и создайте новое. Уже сохранённые результаты предыдущих проверок не изменятся.

### Интерпретация результатов

| Внутренний результат | Значение |
|---|---|
| `evidence_found` | Найден/не найден заданный фрагмент по формальному условию; **не означает полного соответствия НТД** |
| `mismatch` | Предварительное расхождение по утверждённому правилу в извлечённом тексте DOCX; инженер подтверждает |
| `manual` | Нет полного надёжного текста, нужно исследовать PDF/схему/допуск или сам критерий требует инженера |

Автоматическое обнаружение **отсутствия** обязательной фразы в PDF, скане или XLSX никогда не превращается в окончательное нарушение: присваивается `manual`. Не используйте в правилах неподтверждённые или утратившие актуальность ГОСТ/СП. Нормативные документы не входят в дистрибутив — приложенные ТЗ и справочники не содержат полных текстов нормативов.

## Основные маршруты

`GET /` — проекты; `GET /packages/{id}` — комплект; `POST /packages/{id}/catalog` — обязательный перечень; `POST /packages/{id}/scan` — повторная проверка; `POST /packages/{id}/upload` — загрузка; `GET /norms` — нормативный каталог; `POST /norms` — черновик нормы; `POST /norms/{id}/status` — утверждение или отзыв; `GET /packages/{id}/report/{xlsx|docx|pdf}` — отчёт; `GET /health` — состояние сервиса и количество утверждённых нормативных правил.

### Ограничения и дальнейшие задачи

- Протестировать реальную компиляцию, миграции, NAS-монтирование и безопасность на выделенном стенде.
- Обеспечить независимые роли, доступ по объектам, корпоративную авторизацию и HTTPS; провести проверку журналирования/резервирования.
- Добавить точные структурные правила обязательных полей и нормативных форм, затем геометрические допуски по подтверждённым таблицам ГОСТ/СП.
- Включить сравнение ПД/РД и чертежей, поиск расхождений по материалам, журналам и документам качества.
- Определить, нужны ли проекты непосредственно в **Bitrix24**, и тогда реализовать отдельную REST-интеграцию.

Отдельные тестовые кейсы и состояние проверок перечислены в `QA.md`.


## Изменения v0.4

- Корректнее извлекается текст DOCX, когда Word разбил одно слово/реквизит на несколько фрагментов `<w:t>`; сохраняются переходы строк между абзацами.
- Добавлен `required_pattern` для проверки формата реквизита по проверенному инженером выражению. Создание правила не делает его автоматически утверждённым.
- Для смешанных PDF с текстовыми и сканированными страницами повышена осторожность распознавания: отсутствие текста на отдельной странице помечается как частичное извлечение.
- `GET /health` возвращает фактическое количество утверждённых правил, а не постоянное `true`.
- Добавлена миграция `003_norm_patterns.sql` для существующей базы v0.3 и новые модульные тесты.

> **Никакая конкретная ГОСТ/СП-норма не загружена «на веру».** Упоминания нормативов в исходных файлах не равны актуальной правовой базе. Сначала специалист сверяет применимость, редакцию и формулировку пункта, затем вручную утверждает правило в `/norms`. Проект предназначен для внутреннего пилота, не для автоматического юридически значимого заключения.

Краткие шаги настройки — `QUICKSTART_RU.md`. Методика настройки проверки НТД — `docs/NORMS_SETUP_RU.md`.
